########################
ocpp\_device\_model\_API
########################

.. warning::

   **Experimental API** since \2027.04.0.
   This API is exempt from the EVerest stability guarantees and the deprecation
   period. Its channels, operations and message payloads may change or be
   removed in any release without notice until it is promoted to stable. See

   .. container:: lead

      EVerest API definition for OCPP device model owners - CLIENT side (MODULE)

   API for EVerest API clients that add components and variables to the device model of an OCPP service at runtime, next to those of the JSON component config. The client acts for one or more owners. Each variable has one owner, which keeps its value current, receives the writes to it and keeps its persistent attributes across restarts.

   Startup: the client publishes one registration per owner on m2e/registration. Until the OCPP service has asked for the registrations, the module only collects them, keeping the latest one per owner. When the OCPP service asks, the module publishes e2m/get\_registrations so that clients that are already running send their registrations again, and then waits. If cfg\_expected\_owners lists owners, it waits until each of them has registered, at most cfg\_expected\_owners\_timeout\_s seconds; at the deadline it logs the owners still missing. If the list is empty, it waits cfg\_registration\_timeout\_s seconds. It then hands every collected registration to the OCPP service, which starts. The OCPP service does not start before then. After startup, every registration the client publishes is passed on at once, so an owner that missed the deadline can still register, without the monitors of earlier boots.

   The OCPP service answers every registration with e2m/set\_registration\_result, forwards writes to registered variables with a request on e2m/set\_value, and takes the value changes the client reports on m2e/value\_changed. Experimental: this API is exempt from the EVerest stability guarantees and the deprecation period; channels, operations and message payloads may change without further notice until it is promoted to stable.

   Configuration: the cfg\_ settings named in this specification are configuration keys of the ocpp\_device\_model\_API module, set in the EVerest configuration of the module instance the client talks to. cfg\_expected\_owners is a comma separated list of the owners the client registers, empty by default; list every owner, also those whose devices are not always available. cfg\_expected\_owners\_timeout\_s, 60 seconds by default, bounds the wait for them. cfg\_registration\_timeout\_s, 10 seconds by default, is the collection time when no owners are listed. cfg\_request\_reply\_to\_s, 10 seconds by default, is the time the client has to answer one write; the variables of one SetVariables.req are written one after the other, so their number times this timeout has to stay below the message timeout of the CSMS. The module documentation of ocpp\_device\_model\_API and the how-to guide "Add Components to the OCPP Device Model from an External Application" describe these settings in full.
