send_request_get_variables¶

send Send request to transmit the requested variables
Topic
everest_api/1/ocpp_consumer/{module_id}/m2e/get_variables
Reply
Sent to $message.header#/replyTo as receive_reply_get_variables.

Direction: Module to EVerest

Message Request variables application/json

Message send_request_get_variables

Request the variables.

Reads variables using canonical component/variable addressing (e.g. component OCPPCommCtrlr, variable HeartbeatInterval), identical for OCPP 1.6 and 2.x. An empty component.name marks the deprecated OCPP 1.6 legacy key form (variable.name = configuration key); it is only accepted while OCPP 1.6 is active and will be removed per the deprecation policy. A non-empty component.name is never reinterpreted as a configuration key. Each result echoes the requested component_variable and carries a status.

See the OCPPmulti module documentation ("Configuration access" and "Migration from OCPP 1.6 key addressing") for examples and the migration guide.

send_request_monitor_and_get_variables¶

send Send request to monitor the requested variables and read their current values
Topic
everest_api/1/ocpp_consumer/{module_id}/m2e/monitor_and_get_variables
Reply
Sent to $message.header#/replyTo as receive_reply_monitor_and_get_variables.

Direction: Module to EVerest

Message Monitor variables and read their current values application/json

Message send_request_monitor_and_get_variables

Monitor the variables and receive their current values in the reply.

Combination of monitor_variables and get_variables in one call: starts monitoring the given ComponentVariable(s) exactly like monitor_variables, using the same canonical component/variable addressing as get_variables, identical for OCPP 1.6 and 2.x; the empty-component OCPP 1.6 legacy key form is deprecated. Changes to monitored variables are published on the event_data channel and echo the addressing form used at registration. Consecutive calls of this operation will not override but extend the existing monitors. Additionally the reply contains the current (Actual) value of every requested variable, with the same order, addressing echo and status semantics as get_variables. The monitors are registered before the values are read, so no update can be lost: every change from registration on is published on the event_data channel, and the reply reflects each variable's state at some point after registration. The reply is not ordered against the event stream, however: a change around the call may be reported both in the reply and as an event, and an event may arrive before the reply does. Treat event_data as authoritative for a variable once its first event arrived; use the reply value only until then. This allows registering monitors at startup and obtaining the initial values in a single call without losing an update between the first read and the monitor registration.

See the OCPPmulti module documentation ("Configuration access" and "Migration from OCPP 1.6 key addressing") for examples and the migration guide.

Message receive_charging_schedules

Object that contains OCPP charging schedules of all connectors

The object contains one composite charging schedule for each connector id starting from connector 0. Connector 0 contains a schedule for the whole charging station.

The frequency of publication is controlled by PublishChargingScheduleIntervalS (OCPP 2.x) and CompositeScheduleIntervalS (OCPP 1.6)

The duration of the composite schedules is controlled by PublishChargingScheduleDurationS (OCPP 2.x) and RequestCompositeScheduleDurationS (OCPP 1.6)

  • discharge_limit_L3number

  • setpoint_L3number

    Setpoint in chargingRateUnit that the EV should follow on phase L3 as close as possible.
