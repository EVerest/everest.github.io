powermeter_API¶

version 1.1.0AsyncAPI 3.0.0 content type application/jsonlicense Apache-2.0EVerestpowermeter

EVerest API definition for powermeters

API for EVerest API clients implementing powermeter.

Specification: powermeter_API.yaml · pionix:de:everest:powermeter_API

send the client publishes, EVerest consumes (6) receive EVerest publishes, the client consumes (3)

Servers¶

default mqtt

default local MQTT

Host
localhost:1883
Topic prefix
everest_api/1/powermeter/{module_id}
{module_id}

The ID of the module as defined in the EVerest config file.

Operations¶

Client to EVerest¶

send_reply_start_transaction¶

send Send reply for start transaction
Topic
Dynamic: the replyTo address from the request's headers. Answers receive_request_start_transaction.

Request to reply.

This operation is used to handle the request to start a new transaction on the powermeter (for signed metering according to German Eichrecht).

Message Start transaction reply message application/json

Message start_transaction_reply

The start transaction reply message contains the request status. It indicates whether the transaction could be started successfully or not. Further values may be added to the message depending on the value of the status.

Payload

object StartTransactionReply

Return value when a transaction is started.

Definition of StartTransactionReply

Example

send_reply_stop_transaction¶

send Send reply for stop transaction
Topic
Dynamic: the replyTo address from the request's headers. Answers receive_request_stop_transaction.

Request to reply.

This operation is used to handle the request to stop the transaction on the powermeter and ask for the signed metering information in a reply.

Message Stop transaction reply message application/json

Message stop_transaction_reply

The stop transaction reply message contains the request status. It indicates whether the transaction could be stopped successfully or not. If successful the signed meter value report must be provided in this message too.

Payload

object StopTransactionReply

Report returned when a signed transaction is requested to stop. If successful, includes the signed meter value object. In case of an error, an additional error message can be provided.

Definition of StopTransactionReply

Example

send_powermeter_values¶

send Send powermeter values
Topic
everest_api/1/powermeter/{module_id}/m2e/powermeter_values

Direction: Module to EVerest

This operation is used to send a dataset of measured values. The timestamp and the imported energy (in Wh) are required. Other values are optional.

Message Send powermeter values application/json

Message send_powermeter_values

The send powermeter values message contains the measured dataset. It requires a timestamp and the imported energy in Wh at least. Other values are optional.

Payload

object Powermeter

Measured dataset (AC or DC)

Definition of Powermeter

Example

send_capabilities¶

send Send power meter capabilities
Topic
everest_api/1/powermeter/{module_id}/m2e/capabilities

Direction: Module to EVerest

This operation is used to send the capabilities of the power meter. Optional: meters without restrictions do not need to publish this. If supported, publish at least once during start up and on every change. Absence of individual fields means no restriction.

Message Send power meter capabilities application/json

Message send_capabilities

Capabilities of the power meter, e.g. the minimum current above which the meter measures within its accuracy class (required by the German Calibration Law, Eichrecht). Publish at least once during start up and on every change if supported. Absence of individual fields means no restriction.

Payload

object Capabilities

Capabilities of this power meter. All fields are optional; an absent field means no restriction / not supported.

Definition of Capabilities

Example

send_communication_check¶

send Send communication check
Topic
everest_api/1/powermeter/{module_id}/m2e/communication_check
Message Send communication check application/json

Message send_communication_check

Signal to EVerest that communication is good or check shall be stopped

Payload

boolean CommunicationCheck

Send true at least every cfg_communication_check_to_s seconds to signal that the client is alive, otherwise EVerest raises a CommunicationFault, which the next message clears. Send false to stop the check until the module restarts.

Example

receive_request_start_transaction¶

receive Request start transaction
Topic
everest_api/1/powermeter/{module_id}/e2m/start_transaction
Reply
Sent to $message.header#/replyTo as send_reply_start_transaction.

Request to reply.

This operation is used to handle the request to start a new transaction on the powermeter (for signed metering according to German Eichrecht).

Message Start transaction request message application/json

Message start_transaction_req

The start transaction request message contains the required input parameter for starting an OCMF transaction. These values will be included in the signed OCMF packet of the stop transaction reply.

Payload

object

Additional properties allowed.

  • headersobject required
    • replyTostring required

      The topic to which to send the reply. If this information is missing, the command will still be accepted, but no response will be sent.

  • payloadobject requiredStartTransactionRequest

    Definition of StartTransactionRequest

receive_request_stop_transaction¶

receive Request stop transaction
Topic
everest_api/1/powermeter/{module_id}/e2m/stop_transaction
Reply
Sent to $message.header#/replyTo as send_reply_stop_transaction.

Request to reply.

This operation is used to handle the request to stop the transaction on the powermeter and ask for the signed metering information in a reply.

Message Stop transaction request message application/json

Message stop_transaction_req

The stop transaction request message contains the transaction id to stop the corresponding transaction.

Payload

object

Additional properties allowed.

  • headersobject required
    • replyTostring required

      The topic to which to send the reply. If this information is missing, the command will still be accepted, but no response will be sent.

  • payloadstring required

    The transaction id from the start transaction request, as a plain JSON string. An empty string stops all open transactions; EVerest sends it at start-up.

Examples

object

Capabilities of this power meter. All fields are optional; an absent field means no restriction / not supported.

Additional properties forbidden.

    Minimum current in Ampere in import direction (charging) the meter can measure within its accuracy class (e.g. required by German Calibration Law).

  • min_export_current_Anumber

    Minimum current in Ampere in export direction (discharging) the meter can measure within its accuracy class.

OCMFIdentificationFlags string¶
string

  • RFID_PLAIN: Assignment via external RFID card reader
  • RFID_RELATED: Assignment via protected RFID card reader

  • OCPP_NONE: No user assignment by OCPP
  • OCPP_RS: Assignment by OCPP RemoteStart method
  • OCPP_AUTH: Assignment by OCPP Authorize method
  • OCPP_RS_TLS: Assignment by OCPP RemoteStart method, obtained via a secured TLS connection.
  • OCPP_AUTH_TLS: Assignment by OCPP Authorize method, obtained via a secured TLS connection.
  • OCPP_CACHE: Assignment by authorization cache of OCPP
  • OCPP_WHITELIST: Assignment by whitelist from OCPP
  • OCPP_CERTIFIED: A certificate of the backend was used which certifies the user mapping.
  • ISO15118_NONE: no user assignment by ISO 15118
  • ISO15118_PNC: Plug & Charge was used
  • PLMN_NONE: no user assignment
  • PLMN_RING: call
  • PLMN_SMS: short message

OCMFIdentificationLevel string¶
string
  • NONE: There is no user assignment. The other data for user assignment have no significance.
  • HEARSAY: The assignment is unsecured; e.g. by reading an RFID UID.
  • TRUSTED: The mapping can be trusted to some extent, but there is no absolute reliability. Example: Authorization by backend.
  • VERIFIED: The assignment has been verified by the signature component and special measures.
  • CERTIFIED: The assignment was verified by the signature component using a cryptographic signature that certifies the assignment.
  • SECURE: The mapping was established by a secure feature (e.g. secure RFID card, ISO 15118 with plug and charge, etc.).
  • MISMATCH: Error; UIDs do not match.
  • INVALID: Error; certificate not correct (check negative).
  • OUTDATED: Error; referenced trust certificate expired.
  • UNKNOWN: Certificate could not be successfully verified (no matching trust certificate found).
enumNONEHEARSAYTRUSTEDVERIFIEDCERTIFIEDSECUREMISMATCHINVALIDOUTDATEDUNKNOWN
OCMFIdentificationType string¶
string
  • NONE: No assignment available
  • DENIED: Assignment currently not available (due to two-factor authorization)
  • UNDEFINED: Type not specified
  • ISO14443: UID of an RFID card according to ISO 14443. Represented as 4 or 7 bytes in hexadecimal notation.
  • ISO15693: UID of an RFID card according to ISO 15693. Represented as 8 bytes in hexadecimal notation.
  • EMAID: Electro-Mobility-Account-ID according to ISO/IEC 15118 (string with length 14 or 15)
  • EVCCID: ID of an electric vehicle according to ISO/IEC 15118 (maximum length 6 characters)
  • EVCOID: EV Contract ID according to DIN 91286.
  • ISO7812: Identification card format according to ISO/IEC 7812 (credit and bank cards, etc.)
  • CARD_TXN_NR: Card transaction number (CardTxNbr) for a payment with credit or bank card used in a terminal at the charging point.
  • CENTRAL: Centrally generated ID. No exact format defined, can be e.g. a UUID. (OCPP 2.0)
  • CENTRAL_1: Centrally generated ID, e.g. by start via SMS. No exact format defined. (until OCPP 1.6)
  • CENTRAL_2: Centrally generated ID, e.g. by operator start. No exact format defined. (until OCPP 1.6)
  • LOCAL: Locally generated ID. No exact format defined, might be e.g. a UUID. (OCPP 2.0)
  • LOCAL_1: Locally generated ID, e.g. ID generated internally by the charge point. No exact format defined. (until OCPP 1.6)
  • LOCAL_2: Locally generated ID, for other cases. No exact format defined. (until OCPP 1.6)
  • PHONE_NUMBER: International phone number with leading "+".
  • KEY_CODE: User-related private key code. No exact format defined.
enumNONEDENIEDUNDEFINEDISO14443ISO15693EMAIDEVCCIDEVCOIDISO7812CARD_TXN_NRCENTRALCENTRAL_1CENTRAL_2LOCALLOCAL_1LOCAL_2PHONE_NUMBERKEY_CODE

      • OCPP_AUTH: Assignment by OCPP Authorize method
      • OCPP_RS_TLS: Assignment by OCPP RemoteStart method, obtained via a secured TLS connection.

      • OCPP_WHITELIST: Assignment by whitelist from OCPP
      • OCPP_CERTIFIED: A certificate of the backend was used which certifies the user mapping.
      • ISO15118_NONE: no user assignment by ISO 15118
      • ISO15118_PNC: Plug & Charge was used
      • PLMN_NONE: no user assignment
      • PLMN_RING: call
      • PLMN_SMS: short message
