Add Components to the OCPP Device Model from an External Application¶

Warning

The ocpp_device_model_API is currently experimental: its topics and types may change without further notice.

This guide shows how an application outside EVerest adds its own components and variables to the OCPP device model at runtime, so that the CSMS can read, monitor and configure them: a cooling unit, an auxiliary meter or the devices behind a gateway, for example.

The application talks MQTT to the ocpp_device_model_API module. The topics and payloads are specified in docs/source/reference/EVerest_API/ocpp_device_model_API.yaml.

An integrator can also declare custom variables in the component config of libocpp instead. The OCPP module documentation compares the two ways in Custom configuration and telemetry; the trade-offs below add what matters in operation.

The terms this guide uses, such as owner, component config and custom key, are defined in the OCPP Device Model Glossary.

OCPPmulti serves OCPP 1.6 from the same device model. In 1.6 mode, a registered variable is reachable through GetConfiguration and ChangeConfiguration once a configuration key is mapped onto it. The owner declares the key itself with ocpp16_key on the variable, or the integrator maps one in the key mapping file at Ocpp16KeyMappingsPath, see One model for OCPP 1.6 and OCPP 2.x. Only the Actual attribute is reachable that way, and OCPP 1.6 has no monitors: a reported change is seen on the next read. A custom key is looked up at each request, so it is unknown to the CSMS while its owner is not registered.

A declared key lives as long as the registration that declares it: a later registration of the owner replaces the keys, and a release removes them. It is either a key that OCPP 1.6 does not define, or a built-in key stored in OCPP16LegacyCtrlr, such as LightIntensity, which the variable then holds instead, at startup and at runtime alike. The mapping file takes precedence: a key it names for another variable, or a variable it maps to another key, is refused, whether or not its entry is usable. Declaring the key the file maps to the same variable changes nothing, with two exceptions. If the variable cannot be the key’s target, the key is refused with Ocpp16KeyInvalid, as the file’s entry is unusable too. If the file’s entry was dropped at startup because the variable was not registered then, the declared key maps to the variable until the next start, which applies the file’s entry again. Between owners, the first one to register a key keeps it. A variable whose key is refused is not registered and is listed in the registration result, with Ocpp16KeyInUse when the key or the variable belongs to another key, and with Ocpp16KeyInvalid when the key cannot be mapped to the variable: a built-in key that cannot be overridden, a variable without an Actual attribute or, for a built-in key, of another data type. In OCPP 2.x mode the key is ignored. The built-in OCPP16LegacyCtrlr variable of a key that an owner declares stays in the device model, so a 2.x base report still lists it.

A key that the mapping file maps to a built-in OCPP16LegacyCtrlr key needs its variable registered at startup, otherwise the mapping is ignored with an error log and the key keeps its built-in variable until the next start. A ChangeConfiguration.req reaches the owner with source set to OCPP 1.6.

The supported feature profiles and measurands are derived once, after the startup registrations. The component config that EVerest ships defines SupportedFeatureProfiles and the measurands variables, so their registration is rejected with AlreadyDefined until they are removed from it. A profile that OCPPmulti adds when its configuration is present, CostAndPrice or PnC, is added for any registered value of that configuration, false included. Registrations after startup do not change the profiles or measurands.

The rules in this guide come from libocpp’s runtime registry. The details are in lib/everest/ocpp/doc/v2/ocpp_201_device_model_initialization.md.

Owners¶

Every variable of the device model has exactly one definition: either the component config or one owner. An owner is a name the application chooses, one per device for example. Ownership is per variable, so the component config and an owner can contribute different variables to the same component.

For each of its owners, the application:

  • registers the variables with their characteristics, attributes, initial values and monitors,

  • reports every value that changes,

  • applies the writes of the CSMS, and

  • keeps the values of the persistent attributes across restarts.

A registration is held in memory only and is repeated at every start of the OCPP service. The monitors of a variable, the custom monitors of the CSMS included, are stored by component and variable name, and are applied again when the variable is registered again. Its values are not stored by the OCPP service: the application keeps them.

The diagrams in this guide show the application, the API module, the OCPP module and, where it takes part, the CSMS. Solid arrows are commands and publishes, dashed arrows answers.

Configure the API module¶

Add the module to the EVerest configuration and list the owners the application registers:

device_model_api:
  module: ocpp_device_model_API
  config_module:
    cfg_expected_owners: "cooling_unit"
    cfg_expected_owners_timeout_s: 60

Connect it to the device_model requirement of the OCPPmulti module:

ocpp:
  module: OCPPmulti
  connections:
    device_model:
      - module_id: device_model_api
        implementation_id: main

The requirement takes up to 128 connections, one per API module instance. OCPPmulti asks all of them for their registrations at the same time, so the waits of the instances do not add up.

The topics of this module instance are below everest_api/1/ocpp_device_model/device_model_api/, named by its module id. The topics in this guide are relative to that prefix.

The application may start before or after EVerest, so the module collects the registrations for the OCPP module. With cfg_expected_owners, it hands them on as soon as every listed owner registered, at the latest after cfg_expected_owners_timeout_s. It then logs the owners still missing. Without cfg_expected_owners, the module collects registrations for cfg_registration_timeout_s, 10 s by default.

The OCPP service starts only after the module handed the registrations on, so these timeouts delay the connection to the CSMS. Each of them is at most 100 s, below the 120 s after which EVerest aborts a command.

The first start of the OCPP service removes the monitors of the variables that nobody registered. An owner that registers later is still accepted, but the monitors of its variables from earlier boots are gone by then. List every owner in cfg_expected_owners, also those whose devices are not always available.

A gateway with cfg_expected_owners: "meter-1, meter-2" that is already running publishes meter-1 before the OCPP module asks. The module keeps it, prompts the application when the OCPP module asks, and answers as soon as both owners registered:

        sequenceDiagram
    participant App as Application
    participant API as ocpp_device_model_API
    participant OCPP as OCPP module
    App-)API: m2e/registration (meter-1)
    Note over API: kept, not passed on yet
    OCPP->>API: get_registrations()
    API-)App: e2m/get_registrations
    App-)API: m2e/registration (meter-1, again)
    App-)API: m2e/registration (meter-2)
    Note over API: every expected owner registered
    API-->>OCPP: registrations of meter-1 and meter-2
    Note over OCPP: the OCPP service starts
    OCPP->>API: set_registration_result() per owner
    API-)App: e2m/set_registration_result per owner

When meter-2 does not register in time, the module answers without it at the deadline. meter-2 can still register later, but the monitors of its variables from earlier boots are gone:

        sequenceDiagram
    participant App as Application
    participant API as ocpp_device_model_API
    participant OCPP as OCPP module
    OCPP->>API: get_registrations()
    API-)App: e2m/get_registrations
    App-)API: m2e/registration (meter-1)
    Note over API: cfg_expected_owners_timeout_s expires,<br/>meter-2 is logged as missing
    API-->>OCPP: registrations of meter-1
    Note over OCPP: the OCPP service starts and removes<br/>the stored monitors of meter-2
    App-)API: m2e/registration (meter-2), later
    API-)OCPP: registration
    OCPP->>API: set_registration_result(meter-2)
    API-)App: e2m/set_registration_result

Without cfg_expected_owners, the module waits the full cfg_registration_timeout_s after the prompt and answers with everything it collected:

        sequenceDiagram
    participant App as Application
    participant API as ocpp_device_model_API
    participant OCPP as OCPP module
    OCPP->>API: get_registrations()
    API-)App: e2m/get_registrations, no expected owners

    Note over API: cfg_registration_timeout_s expires
    API-->>OCPP: registrations of meter-1 and meter-2
    Note over OCPP: the OCPP service starts

The module also supervises the communication with its clients, see the module documentation.

Register components¶

Publish one registration per owner on m2e/registration:

  • when the application starts, and

  • each time the module publishes e2m/get_registrations, which it does when the OCPP module asks for the registrations. Publish the registration of every owner again, also the ones published before.

A registration names the components of an owner and the variables of each component. This registration of a cooling unit at EVSE 1 adds three variables: a temperature reading, a writable fan speed limit and a mode.

{
  "owner": "cooling_unit",
  "components": [
    {
      "component": { "name": "CoolingUnit", "instance": "1", "evse": { "id": 1 } },
      "variables": [
        {
          "variable": { "name": "Temperature" },
          "characteristics": { "data_type": "decimal", "unit": "Celsius", "supports_monitoring": true },
          "attributes": [{ "type": "Actual", "value": "21.5", "mutability": "ReadOnly" }],
          "monitors": [
            { "type": "UpperThreshold", "value": 70, "severity": 4, "monitor_type": "PreconfiguredMonitor" }
          ]
        },
        {
          "variable": { "name": "FanSpeedLimit" },
          "characteristics": {
            "data_type": "integer",
            "unit": "Percent",
            "min_limit": 0,
            "max_limit": 100,
            "supports_monitoring": false
          },
          "attributes": [{ "value": "80", "mutability": "ReadWrite", "persistent": true }]
        },
        {
          "variable": { "name": "Mode" },
          "characteristics": {
            "data_type": "OptionList",
            "values_list": "Eco,Normal,Boost",
            "supports_monitoring": false
          },
          "attributes": [{ "value": "Normal", "mutability": "ReadWrite" }]
        }
      ]
    }
  ]
}

A registration without owner belongs to the owner named by the module id, device_model_api here. The FanSpeedLimit attribute has no type, so it defaults to the Actual attribute. Because it is persistent, the application stores the value of every write and registers the stored value at the next start, here 80.

The Temperature monitor raises an event when the reported temperature rises above 70 °C, and a second one with cleared set when it falls back. The OCPP service sends both to the CSMS in a NotifyEvent.req, filtered by the monitoring level and base the CSMS set, and queued while offline up to OfflineQueuingSeverity. The application is not told about the events.

The CSMS cannot clear a monitor of either kind. It may change a PreconfiguredMonitor with a SetVariableMonitoring.req that names its id. The monitor keeps its id but becomes a custom monitor (N04.FR.15), which belongs to the CSMS: the CSMS can clear it, and a SetMonitoringBase.req with FactoryDefault or HardWiredOnly deletes it like any custom monitor. A registration matches stored monitors by type and severity and keeps a matched custom monitor in place of the preconfigured one it lists, so a threshold the CSMS changed to 75 is kept when the application registers the variable again, even though the registration still lists 70. Once the CSMS cleared or the monitoring base deleted the custom monitor, the next registration sets up the preconfigured monitor with 70 again. If the CSMS changed the severity, nothing matches: the registration sets up the preconfigured monitor with severity 4 again, next to the custom one. A HardWiredMonitor cannot be changed: a SetVariableMonitoring.req with its id is rejected. It also stays active when the CSMS sets the monitoring base to HardWiredOnly, which deactivates preconfigured monitors.

Keep these rules in mind when choosing names:

  • An instance is either absent or not empty. A component or variable with an empty instance is rejected with InvalidNameKey, because monitors and stored values key an absent instance as an empty one.

  • A name or value longer than the OCPP types allow, a name longer than 50 characters for example, makes the whole registration Invalid, see Check the result.

  • An attribute without mutability is ReadOnly.

  • The variables that the OCPP service writes from its own state are rejected with ReservedVariable, for example AuthCacheCtrlr.Storage, the AvailabilityState of an EVSE and every variable of a NetworkConfiguration slot. The required ones among them must be defined with a value in the component config: OCPPCommCtrlr.MessageTimeout, SecurityCtrlr.Identity and SecurityCtrlr.SecurityProfile, and LocalAuthListCtrlr.Entries when LocalAuthListCtrlr.Available is true.

  • In OCPP 1.6 mode, a variable whose ocpp16_key is refused is rejected with Ocpp16KeyInUse or Ocpp16KeyInvalid, see the OCPP 1.6 paragraph at the top of this guide.

Check the result¶

The OCPP module answers each registration it applies on e2m/set_registration_result, at startup and at runtime. A registration replaced by a newer one of the same owner before it was applied, at startup or before the OCPP service started, is answered only through the newer one. A registration the device model fails to apply, when its storage fails for example, is answered Rejected: the owner is dropped with its earlier registration, and the application registers it again. The application does not reply. Here cooling_unit is accepted, and meter-1 is refused because another module instance holds that owner name, see Register several owners:

        sequenceDiagram
    participant App as Application
    participant API as ocpp_device_model_API
    participant OCPP as OCPP module
    OCPP->>API: set_registration_result(cooling_unit)
    API-)App: e2m/set_registration_result, Accepted
    OCPP->>API: set_registration_result(meter-1)
    API-)App: e2m/set_registration_result, OwnerInUse

In the usual case nothing is rejected:

{ "owner": "cooling_unit", "status": "Accepted", "rejected": [] }

When the component config defines CoolingUnit.Mode already, only that variable is rejected, and defined_by names the owner of the definition:

{
  "owner": "cooling_unit",
  "status": "Accepted",
  "rejected": [
    {
      "component": { "name": "CoolingUnit", "instance": "1", "evse": { "id": 1 } },
      "variable": { "name": "Mode" },
      "reason": "AlreadyDefined",
      "defined_by": "COMPONENT_CONFIG"
    }
  ]
}

The application receives no writes to a rejected variable and does not report its values.

A registration that does not match the schema of the API, a unit of more than 16 characters, a component name of more than 50 or an unknown property for example, is answered by the API module with Invalid and not passed on. An earlier registration of the owner stays in place:

{ "owner": "cooling_unit", "status": "Invalid", "rejected": [] }

The result names the owner of the registration, or the module id when it names none or its owner cannot be read: when the message is not a JSON object, or its owner is not a non-empty string. The module logs every such message.

Every application connected to the module instance receives every result on the same topic, so an application picks its own by owner. A malformed registration is answered Invalid for the owner it names, even one that another application holds, and changes nothing; an application ignores an Invalid it did not cause.

Register several owners¶

An application that fronts several devices, a Modbus gateway for two auxiliary meters for example, names one owner per device and publishes one registration for each. Each device then has its own registration, which the application can replace or remove on its own:

{
  "owner": "meter-1",
  "components": [
    {
      "component": { "name": "AuxiliaryMeter", "instance": "1" },
      "variables": [
        {
          "variable": { "name": "Power" },
          "characteristics": { "data_type": "decimal", "unit": "W", "supports_monitoring": true },
          "attributes": [{ "value": "1450", "mutability": "ReadOnly" }]
        }
      ]
    }
  ]
}

{
  "owner": "meter-2",
  "components": [
    {
      "component": { "name": "AuxiliaryMeter", "instance": "2" },
      "variables": [
        {
          "variable": { "name": "Power" },
          "characteristics": { "data_type": "decimal", "unit": "W", "supports_monitoring": true },
          "attributes": [{ "value": "0", "mutability": "ReadOnly" }]
        }
      ]
    }
  ]
}

Both owners belong in cfg_expected_owners, here "meter-1, meter-2".

An owner name belongs to the module instance that registered it first, until it is released. When a second instance registers meter-1, nothing of that registration reaches the device model:

{ "owner": "meter-1", "status": "OwnerInUse", "rejected": [] }

Apply writes¶

The OCPP module checks a write against the characteristics and the mutability of the variable, then passes it on as a request on e2m/set_value. The request names its owner, so a gateway knows which device to pass it on to:

{
  "headers": {
    "replyTo": "everest_api/1/ocpp_device_model/device_model_api/m2e/reply/2b0e6a41-8c1f-4f57-9d0e-5f3c1a7b9e10"
  },
  "payload": {
    "owner": "cooling_unit",
    "component": { "name": "CoolingUnit", "instance": "1", "evse": { "id": 1 } },
    "variable": { "name": "FanSpeedLimit" },
    "attribute_type": "Actual",
    "value": "60",
    "source": "csms"
  }
}

source is csms for a SetVariables.req, OCPP 1.6 for a ChangeConfiguration.req in OCPP 1.6 mode, and otherwise the source that the local caller named, an application of the ocpp_consumer_API for example.

Publish the status on the replyTo topic, "Accepted" for example. It goes to the CSMS as it is:

        sequenceDiagram
    participant App as Application
    participant API as ocpp_device_model_API
    participant OCPP as OCPP module
    participant CSMS
    CSMS->>OCPP: SetVariables.req
    OCPP->>API: set_value(request)
    API->>App: e2m/set_value with replyTo
    App-->>API: "Accepted" on replyTo
    API-->>OCPP: Accepted
    OCPP-->>CSMS: SetVariables.conf Accepted
    Note over App,CSMS: a write the owner rejects
    CSMS->>OCPP: SetVariables.req
    OCPP->>API: set_value(request)
    API->>App: e2m/set_value with replyTo
    App-->>API: "Rejected" on replyTo
    API-->>OCPP: Rejected
    OCPP-->>CSMS: SetVariables.conf Rejected
    Note over App,CSMS: a write that applies at the next start
    CSMS->>OCPP: SetVariables.req
    OCPP->>API: set_value(request)
    API->>App: e2m/set_value with replyTo
    App-->>API: "RebootRequired" on replyTo
    API-->>OCPP: RebootRequired
    OCPP-->>CSMS: SetVariables.conf RebootRequired
    Note over App,CSMS: a write the application does not answer in time
    CSMS->>OCPP: SetVariables.req
    OCPP->>API: set_value(request)
    API->>App: e2m/set_value with replyTo
    Note over API: cfg_request_reply_to_s expires
    API-->>OCPP: Rejected
    OCPP-->>CSMS: SetVariables.conf Rejected
    App-->>API: late reply on replyTo
    Note over API: ignored and logged

  • Accepted: the owner applied exactly 60. The OCPP service stores the value in memory, so the application does not report it again on m2e/value_changed.

  • RebootRequired: the owner kept exactly 60, but the value takes effect only at the next start. The OCPP service does not store it: until then, reads return the current value, 80 in the example. The application keeps the new value and registers it at the next start, and does not report it on m2e/value_changed before it takes effect.

  • Rejected: the owner did not apply the value. This includes a value it would only apply in a changed form. A fan that runs at most at 55 % rejects the write rather than accepting it and clamping it.

A write to a WriteOnly attribute reaches the application in the same way. The CSMS cannot read the value back: GetVariables.req is answered Rejected, and reports leave the value out.

Without a reply within cfg_request_reply_to_s, 10 s by default, the write is Rejected. Reject a write that the device does not confirm in time.

Writes are delivered one at a time, so a write that is answered late delays the following ones: each unanswered write holds them up by cfg_request_reply_to_s. libocpp applies the entries of a SetVariables.req one after the other and waits for each answer, so the timeout applies per variable, not per request. An application that does not answer makes a request with N variables take N times cfg_request_reply_to_s, 50 s for 5 variables at the default. Keep that product below the message timeout of the CSMS, which waits for its SetVariables.conf meanwhile. Otherwise the CSMS can time out while the request is still being worked through, and if it retries, a write the application applies after the deadline leaves the device and the device model in disagreement.

The number of entries in one request is bounded by DeviceDataCtrlr.ItemsPerMessage with instance SetVariables (B05.FR.11), so the worst case is that value times cfg_request_reply_to_s. It is 100 in the component config that EVerest ships. The value applies to every SetVariables.req, not only to writes to registered variables, so lowering it is a trade-off. The OCPP module answers a SetVariables.req with more entries than that with a CALLERROR OccurrenceConstraintViolation and applies none of them, as it does for a GetVariables.req.

Report changes¶

Publish each value the device changes itself on m2e/value_changed. The OCPP service answers reads from the values it holds, so a change that is not reported does not reach the CSMS, unless a monitor is registered for it.

        sequenceDiagram
    participant App as Application
    participant API as ocpp_device_model_API
    participant OCPP as OCPP module
    participant CSMS
    Note over App: the temperature rises
    App-)API: m2e/value_changed
    API-)OCPP: value_changed
    Note over OCPP: stores the value and<br/>evaluates the monitors
    OCPP-)CSMS: NotifyEvent.req, when a monitor triggers
    
{
  "owner": "cooling_unit",
  "component": { "name": "CoolingUnit", "instance": "1", "evse": { "id": 1 } },
  "variable": { "name": "Temperature" },
  "value": "48.25"
}

Without owner, a report belongs to the owner named by the module id. Without attribute_type, it reports the Actual attribute; Target, MinSet and MaxSet are reported the same way, with attribute_type set.

A report is applied as it arrives, so a write that is in progress when the device changes the value may overwrite it.

The OCPP module handles registrations and reports in parallel, so a report published right after a registration may reach it first. Such a report is kept and applied once the registration is, also when the registration adds the variable. A kept report is dropped when the registration of its owner is refused or releases the owner. Each module instance keeps at most 64 reports, the latest per variable, for owners that are not registered; beyond that the oldest one is dropped.

A report of a value that does not fit the data type or the values_list of the variable is ignored, and so is a report for an owner that another module instance holds or that is never registered. A report has no reply, so the rejection is only logged. min_limit and max_limit bound the writes of the CSMS, not the reports of the owner.

Replace or release an owner¶

A registration replaces everything its owner registered before. The registrations of the other owners stay. A registration with an empty components list removes the variables of the owner and releases the owner name:

{ "owner": "meter-2", "components": [] }

Here the gateway adds meter-3 for a device connected at runtime, then releases meter-2. meter-3 was not part of the startup answer, so the monitors of its variables from earlier boots are gone:

        sequenceDiagram
    participant App as Application
    participant API as ocpp_device_model_API
    participant OCPP as OCPP module
    App-)API: m2e/registration (meter-3, a new device)
    API-)OCPP: registration
    OCPP->>API: set_registration_result(meter-3)
    API-)App: e2m/set_registration_result
    App-)API: m2e/registration (meter-2, no components)
    API-)OCPP: registration
    OCPP->>API: set_registration_result(meter-2)
    API-)App: e2m/set_registration_result
    Note over App,OCPP: the owner name meter-2 is free again

Once the module handed the collected registrations on, it passes each further registration on at once. That registration is not ordered against the collected ones and may reach the OCPP module first: a release would then be undone by the collected registration that still holds the owner. To replace or release an owner registered at startup, wait for its e2m/set_registration_result first.

Relation to the ocpp_consumer_API¶

The ocpp_consumer_API sees the complete device model, registered variables included:

  • m2e/get_variables reads a registered variable from the values the OCPP service holds, and m2e/monitor_variables watches it, like any other variable.

  • m2e/set_variables to a ReadWrite registered variable reaches the owner on e2m/set_value, like a write of the CSMS, and the owner’s answer is the answer. A write to a ReadOnly registered variable is rejected: its owner reports the value.

  • An owner reports its own changes on m2e/value_changed of this API, not with m2e/set_variables of the ocpp_consumer_API.

Move a variable from the component config to an owner¶

A variable declared in the component config, such as telemetry declared there, moves to an owner in three steps:

  1. Remove the variable from the component config. For a component of its own, delete the variable from its JSON file, or the whole file. For a standardized component, place a copy of the component without the variable under component_config/custom, which replaces the standardized one.

  2. Register the variable, with the characteristics, attributes and monitors it had, and with its current value. List its owner in cfg_expected_owners.

  3. Report its changes on m2e/value_changed instead of writing them through the ocpp interface or the ocpp_consumer_API.

The monitors of the variable, the custom monitors of the CSMS included, carry over: the device model keeps them by component and variable name and applies them when the owner registers the variable at startup. An owner that misses the registration deadline loses them. The stored value does not carry over; the owner registers its own. Until the variable is removed from the component config, its registration is rejected with the variable named in defined_by.

Trade-offs¶

Compared with a variable in the component config, a registered variable:

  • exists only while its owner is registered. Before the registration, and after a release, the CSMS gets UnknownComponent or UnknownVariable for it, and GetBaseReport leaves it out.

  • delays the start of the OCPP service, and with it the connection to the CSMS, by the time the API module waits for the registrations: until every owner in cfg_expected_owners registered, at most cfg_expected_owners_timeout_s, or cfg_registration_timeout_s without expected owners.

  • loses its monitors from earlier boots, the custom monitors of the CSMS included, when its owner misses the registration deadline.

  • slows down SetVariables.req by up to cfg_request_reply_to_s per variable when its owner does not answer.

In return, the application that knows the value keeps it current, validates the writes of the CSMS itself, and keeps the value across restarts.
