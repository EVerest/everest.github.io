ocpp_device_model_API¶

Warning

Experimental API since 2027.04.0. This API is exempt from the EVerest stability guarantees and the deprecation period. Its channels, operations and message payloads may change or be removed in any release without notice until it is promoted to stable. See the policy on experimental components and the experimental feature index.

experimentalversion 1.0.0AsyncAPI 3.0.0 content type application/jsonlicense Apache-2.0EVerestOCPP

EVerest API definition for OCPP device model owners - CLIENT side (MODULE)

API for EVerest API clients that add components and variables to the device model of an OCPP service at runtime, next to those of the JSON component config. The client acts for one or more owners. Each variable has one owner, which keeps its value current, receives the writes to it and keeps its persistent attributes across restarts.

Startup: the client publishes one registration per owner on m2e/registration. Until the OCPP service has asked for the registrations, the module only collects them, keeping the latest one per owner. When the OCPP service asks, the module publishes e2m/get_registrations so that clients that are already running send their registrations again, and then waits. If cfg_expected_owners lists owners, it waits until each of them has registered, at most cfg_expected_owners_timeout_s seconds; at the deadline it logs the owners still missing. If the list is empty, it waits cfg_registration_timeout_s seconds. It then hands every collected registration to the OCPP service, which starts. The OCPP service does not start before then. After startup, every registration the client publishes is passed on at once, so an owner that missed the deadline can still register, without the monitors of earlier boots.

The OCPP service answers every registration with e2m/set_registration_result, forwards writes to registered variables with a request on e2m/set_value, and takes the value changes the client reports on m2e/value_changed. Experimental: this API is exempt from the EVerest stability guarantees and the deprecation period; channels, operations and message payloads may change without further notice until it is promoted to stable.

Configuration: the cfg_ settings named in this specification are configuration keys of the ocpp_device_model_API module, set in the EVerest configuration of the module instance the client talks to. cfg_expected_owners is a comma separated list of the owners the client registers, empty by default; list every owner, also those whose devices are not always available. cfg_expected_owners_timeout_s, 60 seconds by default, bounds the wait for them. cfg_registration_timeout_s, 10 seconds by default, is the collection time when no owners are listed. cfg_request_reply_to_s, 10 seconds by default, is the time the client has to answer one write; the variables of one SetVariables.req are written one after the other, so their number times this timeout has to stay below the message timeout of the CSMS. The module documentation of ocpp_device_model_API and the how-to guide “Add Components to the OCPP Device Model from an External Application” describe these settings in full.

Specification: ocpp_device_model_API.yaml · pionix:de:everest:ocpp_device_model_API

Operations¶

Client to EVerest¶

send_reply_set_value¶

send Send reply to a set value request
Topic
Dynamic: the replyTo address from the request's headers. Answers receive_request_set_value.

Direction: Module to EVerest

Message Reply to a set value request application/json

Message send_reply_set_value

Accepted: the owner applied exactly the written value; the OCPP service stores it, so the client does not report it on m2e/value_changed. RebootRequired: the owner kept exactly the written value and applies it at the next start; the OCPP service keeps the current value, and the client registers the new value at the next start. Rejected: the owner did not apply the value, also when it would apply another one, a clamped one for example. UnknownComponent, UnknownVariable and NotSupportedAttributeType are returned to the CSMS as they are.

Payload

string SetVariableStatus

Outcome of a write

enumAcceptedRejectedUnknownComponentUnknownVariableNotSupportedAttributeTypeRebootRequired

send_registration¶

send Send a registration
Topic
everest_api/1/ocpp_device_model/{module_id}/m2e/registration

Direction: Module to EVerest

Message Registration of one owner application/json

Message send_registration

Adds an owner, or replaces everything an owner registered before; the registrations of the other owners stay. Before the OCPP service has asked for the registrations, the module collects them. After that, each one is passed on at once, and is answered on e2m/set_registration_result. An empty components list removes everything the owner registered and releases the owner name. A registration passed on at once is not ordered against the answer to the request for registrations, and may reach the OCPP service before it. To replace or release an owner registered at startup, wait for its e2m/set_registration_result first: it follows the answer. A registration that does not fit the schema, a string beyond its maximum length for example, is not passed on and is logged. It is answered with Invalid on e2m/set_registration_result, for the owner it names, or for the module id when it names none or its owner cannot be read. An earlier registration of the owner stays in place.

Payload

object Registration

Everything one owner adds to the device model. It replaces what the same owner registered before.

Definition of Registration

send_value_changed¶

send Send a value change
Topic
everest_api/1/ocpp_device_model/{module_id}/m2e/value_changed

Direction: Module to EVerest

Message Value change of a registered variable application/json

Message send_value_changed

Published when the owner changed a value itself. Report every change: the OCPP service holds the values in memory and serves reads from there. A report published right after a registration is applied once the registration is; it is dropped when the registration is refused or releases the owner. At most 64 reports for owners that are not registered are kept, the oldest is dropped beyond that. A report that does not fit the variable, or for an owner that another module instance holds or that is never registered, is ignored and logged.

Payload

object ValueChange

A value of a registered variable that its owner changed itself

Definition of ValueChange

Message send_communication_check

Signal to EVerest that communication is good or check shall be stopped

Payload

boolean CommunicationCheck

Send true at least every cfg_communication_check_to_s seconds to signal that the client is alive, otherwise EVerest raises a CommunicationFault, which the next message clears. Send false to stop the check until the module restarts.

receive_get_registrations¶

Message receive_get_registrations

receive_set_registration_result¶

receive Receive the result of a registration
Topic
everest_api/1/ocpp_device_model/{module_id}/e2m/set_registration_result

Direction: EVerest to Module

Message Result of a registration application/json

Message receive_set_registration_result

The outcome of one registration, published once for every registration the OCPP service applied, at startup and at runtime. A registration replaced by a newer one of the same owner before it was applied, at startup or before the OCPP service started, is answered only through the newer one. A registration the device model fails to apply is answered with Rejected, and its owner is dropped. No reply is expected. A registration that does not match the schema is answered with Invalid by this module, for its owner, or for the module id when it names none or its owner cannot be read, because it is not a JSON object or its owner is not a non-empty string. Every client of the module receives every result, so a client picks its own by owner; an Invalid for an owner the client holds may come from another client's malformed registration naming it, which changes nothing.

Payload

object RegistrationResult

The outcome of the registration of one owner

Definition of RegistrationResult

receive_request_set_value¶

receive Request to set a value
Topic
everest_api/1/ocpp_device_model/{module_id}/e2m/set_value
Reply
Sent to $message.header#/replyTo as send_reply_set_value.

Direction: EVerest to Module

Message Request to set a value application/json

Message receive_request_set_value

A write to an attribute of a registered variable, from the CSMS or from the OCPP service itself. The OCPP service checked the value against the characteristics and the mutability of the variable already. Writes to WriteOnly attributes are forwarded the same way. Requests are delivered one at a time. Reply within cfg_request_reply_to_s, 10 seconds by default: without a reply in time, the write is answered Rejected, and until then each unanswered write holds up the following ones by cfg_request_reply_to_s.

RegisteredMonitorType string¶

RegistrationStatus string¶
string

Whether a registration was passed on to the device model - Accepted: Passed on; single variables may still be rejected - OwnerInUse: Another module uses the owner name already. Nothing of the registration was passed on. - Invalid: The registration does not match this schema, a name longer than 50 characters or an unknown property for example. This module answers it itself; nothing was passed on, and an earlier registration of the owner stays in place.

  • Rejected: The OCPP service failed to apply the registration, because its storage failed for example. The owner is dropped: neither this registration nor an earlier one of the owner stays in the device model, and the owner name is free. The client may register the owner again.
enumAcceptedOwnerInUseInvalidRejected
RegistrationRejectionReason string¶
string

Why a variable of a registration was rejected - AlreadyDefined: The component config or another owner defines the variable already, or the registration defines it twice

  • NoAttributes: The variable has no attributes - ReservedOwner: The owner is COMPONENT_CONFIG - InvalidNameKey: The component or the variable has an empty instance, or the component an EVSE or connector id of 0. A name or value beyond its length is answered with the status Invalid instead.
  • ReservedVariable: Only the component config may define the variable, as the OCPP service writes it from its own state
  • Ocpp16KeyInUse: OCPP 1.6 only. The ocpp16_key of the variable, or the variable itself, belongs to another key: a built-in key, an entry of the key mapping file or the key of another owner's variable
  • Ocpp16KeyInvalid: OCPP 1.6 only. The ocpp16_key cannot be mapped to the variable: a built-in key that cannot be overridden, a variable that holds connection configuration or that OCPP 1.6 computes, a variable without an Actual attribute or, for a built-in key, with another data type than its built-in variable
