How the device model is composed¶

OCPPmulti keeps one device model, in one database, for OCPP 1.6 and OCPP 2.x alike. An OCPP 2.x CSMS reads and writes it with GetVariables and SetVariables, an OCPP 1.6 CSMS with GetConfiguration and ChangeConfiguration, and EVerest modules reach it through the ocpp interface. Five contributors fill it:

  • the component configuration, the JSON files in which the integrator defines the station;

  • libocpp, which computes the availability states;

  • the components EVerest provides, reported by the modules the OCPP module is connected to;

  • the EVerest module configuration views, backed by the configuration service;

  • external providers, components that bring their own configuration and telemetry.

Every variable has exactly one owner. libocpp’s device model composes the model from what the owners bring, serves every read from memory and routes every write to the owner.

Note

External providers and the ocpp_device_model_provider API arrive in their own pull request, after the single device model database. They are described here already so that the page shows the complete design.

One model for OCPP 1.6 and OCPP 2.x¶

The device model backs configuration and telemetry of both protocol versions. OCPP 2.x addresses it directly with GetVariables, SetVariables and GetBaseReport. OCPP 1.6 knows only configuration keys, so OCPPmulti maps each key onto a component and variable: a built-in mapping for the standard keys, custom mappings from Ocpp16KeyMappingsPath, and the OCPP16LegacyCtrlr component for keys without a standardized counterpart. GetConfiguration and ChangeConfiguration read and write the mapped variables, whichever contributor owns them; a variable without a mapping is invisible to an OCPP 1.6 CSMS. OCPP 1.6 has no variable monitoring, so telemetry such as EVSE / Power reaches a 1.6 CSMS only through MeterValues. The ocpp interface sees every variable in both modes.

Telemetry in the component configuration¶

Until external providers are available, an integrator’s own telemetry can be declared in the component configuration and reported through the ocpp interface, from an EVerest module or a client of the ocpp_consumer_API. This is supported as an interim; the variable moves to a provider once providers exist. The component configuration is meant for configuration, so the variable has to be declared for the purpose:

  • mutability ReadOnly: the CSMS cannot write the value, the ocpp interface can.

  • persistent false: otherwise every reported value is a database write. The value then lives in memory and, after a restart, is the value from the component configuration until the first report.

  • No minLimit or maxLimit, or limits that cover every value the source can report. A value outside them is rejected like a configuration write, and the variable keeps its last value, so a reading out of range, typically a fault, reaches neither the CSMS nor the monitors on the variable.

  • supportsMonitoring true if the CSMS may monitor the variable.

For example, a coolant temperature in a custom component file:

{
  "name": "CoolingCtrlr",
  "type": "object",
  "properties": {
    "CoolantTemperature": {
      "variable_name": "CoolantTemperature",
      "characteristics": {
        "supportsMonitoring": true,
        "dataType": "decimal",
        "unit": "Celsius"
      },
      "attributes": [
        {
          "type": "Actual",
          "mutability": "ReadOnly",
          "persistent": false,
          "value": 0
        }
      ],
      "type": "number"
    }
  }
}

A new variable, or a change to its declaration, takes effect at the next start of the module.

The component configuration¶

The JSON files under DeviceModelConfigPath define the station as the integrator ships it: the standardized controllers, the network connection slots, InternalCtrlr and any custom component. They are described in Device model configuration via component configs.

At the first start the files seed the database. At every later start their structure is applied again, so a new or changed component, variable or attribute reaches the database, while values written at runtime are kept. From then on the database holds the values. The module needs no EVSE or Connector component configuration; they are registered at runtime.

A few of these variables are maintained by libocpp rather than by the CSMS: OCPPCommCtrlr / ActiveNetworkProfile and NetworkConfigurationPriority and SecurityCtrlr / SecurityProfile, which follow the connection in use; OCPP16LegacyCtrlr / NumberOfConnectors and OCPPCommCtrlr / FieldLength of the ISO 15118 certificate response, filled at every start; and AuthCacheCtrlr / Storage and LocalAuthListCtrlr / Entries, whose maxLimit the integrator configures to bound the authorization cache and the local list.

libocpp¶

libocpp registers AvailabilityState of the charging station, of every EVSE and of every connector under the owner OCPP_STACK, each unless the component configuration defines it. The value comes from the same state machine that drives StatusNotification, so GetVariables and StatusNotification always agree. The standardized ChargingStation component configuration defines the charging station’s AvailabilityState, and component configurations written for earlier versions may define those of the EVSEs and connectors; libocpp leaves such a definition in place and writes its value in the same way. The OCPP 1.6 stack does not use them, so the OCPP 1.6 path skips the registration.

Monitors the CSMS sets on any of these variables survive a restart as well.

EVerest module configuration views¶

The configuration of the other EVerest modules is visible in the device model under the owner EVEREST_CONFIG:

  • One component per module, named after the module type, with the module id as instance and the EVSE and connector taken from the module’s mapping: EvseManager with instance connector_1 on EVSE 1.

  • One variable per configuration parameter, named like the parameter; a parameter of an implementation is prefixed with the implementation id.

  • Data type, unit, limits and mutability come from the manifest. WriteOnly parameters cannot be monitored, and reports leave out their values.

  • The values stay in the configuration service, which keeps them across restarts.

Which modules are visible follows the access block of the OCPP module in the EVerest configuration: reading needs read access to the module, writing additionally needs write access. A ReadOnly parameter cannot be changed through OCPP.

A write the CSMS makes is forwarded to the configuration service, and its answer is the answer to the CSMS: Accepted, Rejected, or RebootRequired for a parameter the module applies only at its next start. A change made elsewhere, for example through the Configuration API, shows up in GetVariables and in variable monitors right away. A change that the module applies only at its next start does not: until then, GetVariables returns the value in effect.

External providers¶

An integrator can bring their own configuration and telemetry into the device model from outside the EVerest process tree: a vendor controller with its settings, a display, a payment terminal, a cloud agent. The EVerest interface ocpp_device_model_provider carries it, and the bridge module ocpp_device_model_provider_API exposes it on the EVerest API, so a client needs no EVerest module of its own. Each provider is registered as an owner of its own, EXT:<module_id>.

A provider hands OCPPmulti its registration: the complete set of components it owns, with characteristics, attributes and current values. OCPPmulti asks for it at start and whenever the provider signals a change; a new registration replaces the previous one. A write from the CSMS, already validated against the registered characteristics, is handed to the provider, which answers Accepted, RebootRequired or Rejected. A value the provider changes itself is reported to the device model like a value EVerest provides. Whether a variable is only reported or also written follows the mutability the provider registers.

A provider owns its values, whatever persistent says; OCPPmulti stores nothing of them, so the provider keeps them across its own restarts. Monitors the CSMS places on a provider’s variables are stored by OCPPmulti and apply again when the provider registers at the next start.

A provider may register components of its own, such as VendorCtrlr / DisplayBrightness; vendor variables on a standard component, such as a vendor variable on EVSE; and standard configuration variables the component configuration leaves out, such as OCPPCommCtrlr / HeartbeatInterval. To hand such a variable to a provider, the integrator places a component configuration of the same component without the variable under component_config/custom, which replaces the standardized one; the variable’s monitors carry over to the provider’s registration. A provider that registers a standard variable must use the data type the standard defines, since libocpp reads it. A provider may not register what the component configuration defines, libocpp writes from its own state or EVerest reports, such as AvailabilityState, SecurityCtrlr / Identity, a network connection profile or EVSE / Power; such a variable is rejected and the rest of the registration is applied.

Rules of composition¶

The device model applies the same few rules to every contributor:

  • One definition per variable. A variable is defined by the component configuration or by one runtime owner. A registration of a variable that the component configuration or another runtime owner defines is rejected, and the rest of the registration is applied. A component may combine both: the component configuration can add variables to EVSE or Connector, as long as it leaves out those EVerest registers.

  • Conflicts are errors. A variable defined twice is a conflict. OCPPmulti logs them at every start as one error that names each variable and what to remove from the component configuration. By default the station starts anyway, so that a station whose component configuration is outdated after an update stays reachable for the CSMS; with FailOnDeviceModelConflicts the module does not start.

  • A variable can move from the component configuration to a registration. When an update removes a variable from the component configuration, or the whole file of its component, and a runtime owner registers it, its monitors carry over: the device model keeps them by name when the variable leaves the component configuration and applies them when the owner registers it. The value is not kept; the owner registers its own.

  • persistent describes the value, not where it is stored. For an owner that answers writes itself, the owner keeps the value; for every other owner, the device model stores a persistent attribute in its database.

  • A read returns the value in effect. Accepted stores the value in the device model, whoever owns the variable, so a GetVariables after a SetVariables returns the value the CSMS set. After RebootRequired the device model keeps the previous value: the owner holds the value written for the next start and registers with it then. OCPP 2.x leaves open what a read returns until then; B10.FR.01 allows either answer for a NetworkConfigurationPriority change that applies after a reboot.

  • libocpp writes what it owns. libocpp sets a variable it registered or one of the component configuration variables it maintains. A write of its own to a variable an external provider took over, such as the heartbeat interval from the BootNotification response, reaches the provider like a CSMS write.

  • Every write reaches the owner. The CSMS writes across all contributors; that is what OCPP is for. The ocpp interface, and with it the ocpp_consumer_API module, is the local channel, the integrator’s own code that OCPPmulti trusts: it writes ReadOnly variables of the component configuration, which the integrator maintains that way, and writes a registered variable like the CSMS does, through its owner and only when it is ReadWrite. A ReadOnly registered variable is a value its owner reports, so a write to it is rejected: the modules report the values they provide, and an external provider changes its own values.

Startup¶

The device model is complete before the charge point reports it for the first time. On the OCPP 2.x and the OCPP 1.6 path alike, OCPPmulti

  1. collects what the connected modules report and asks every external provider for its registration;

  2. opens the device model database and applies the component configuration;

  3. registers the components EVerest provides, the EVerest module configuration views and the external providers;

  4. registers the availability states (OCPP 2.x only);

  5. reports the conflicts between the component configuration and the registrations, and stops if FailOnDeviceModelConflicts is set;

  6. constructs the charge point, which checks the composed model for completeness, and connects to the CSMS.

External providers are up when OCPPmulti starts; the stack relies on that. A registration a provider changes at runtime is applied live: visible to GetVariables at once, and to the CSMS with its next GetBaseReport.

Reads, writes and changes¶

Reads are served from memory, on every channel: the CSMS, the ocpp interface and with it the ocpp_consumer_API module see the complete composed model. A write goes to whoever owns the variable, and every owner has its own way of reporting a change. The sequences below show both, per contributor. Each one ends the same way: the device model updates memory and evaluates the monitors of the variable, which is where a NotifyEvent originates.

    DM->>DM: update memory, evaluate monitors
    DM-->>API: Accepted
    Note over CSMS,DB: Write by libocpp
    LIB->>DM: ActiveNetworkProfile changed
    DM->>DB: store, if the attribute is persistent
    DM->>DM: update memory, evaluate monitors

The database is written only for persistent attributes, which component configuration attributes are unless the JSON says otherwise. The ocpp interface is the local channel and also writes ReadOnly variables, since ReadOnly models the CSMS contract; see Configuration access.

EVerest module configuration views¶

        sequenceDiagram
    participant CSMS
    participant DM as device model
    participant V as configuration views
    participant CS as configuration service
    participant CA as Configuration API
    Note over CSMS,CA: Write by the CSMS
    CSMS->>DM: SetVariables EvseManager(connector_1).session_logging = false
    DM->>DM: validate
    DM->>V: write
    V->>CS: set parameter
    CS-->>V: RebootRequired
    V-->>DM: RebootRequired
    DM->>DM: keep memory
    DM-->>CSMS: RebootRequired
    CSMS->>DM: GetVariables EvseManager(connector_1).session_logging
    DM-->>CSMS: true, the value the module runs with
    Note over CSMS,CA: Read through the Configuration API until the restart
    CA->>CS: get session_logging
    CS-->>CA: true, the value the module runs with
    Note over CSMS,CA: Change through the Configuration API
    CA->>CS: set session_logging = true
    CS-)V: change notification
    V->>DM: value changed
    DM->>DM: update memory, evaluate monitors

Memory changes only when the configuration service answered Accepted. After RebootRequired the module keeps running with its previous value until the next start, and so does the device model: the CSMS reads the previous value until the views register the new one at the next start, like for every other owner. Until then the Configuration API answers a read with the value the module runs with as well, unless the request sets force_read_from_db. A change through the Configuration API that the module applies at once is reported to the device model when the configuration service delivers it; one that waits for the next start is not. A write from the ocpp interface to a ReadWrite view reaches the configuration service like a write from the CSMS.

Known gap

If the CSMS and a second writer, such as the Configuration API, change the same parameter within milliseconds, the device model can keep the value of the CSMS while the module runs with the value of the second writer. The CSMS then reads the outdated value, and monitors are evaluated against it, until the parameter changes again or OCPPmulti restarts.

The configuration service applies both changes in order, but OCPPmulti handles the answer to its own write and the notification of the other change on different threads, and nothing orders the two when they reach the device model.

The module reports every value it provides, the DER capability included. A reported value must fit the data type and the value list of the variable; limits bound what the CSMS may set, not what the module reports. DER Enabled is the one variable of this group the CSMS, or the ocpp interface, writes, and the device model stores it. A write to any other variable of this group is rejected, from the ocpp interface as well, since the module reports them.

The CSMS waits on the same call as the client, so a client that does not answer in time gets Rejected on its behalf. A write from the ocpp interface to a ReadWrite variable of a provider reaches the provider like a write from the CSMS.

What the database stores¶

The database at DeviceModelDatabasePath keeps three things:

  • the component configuration: its structure and the values of its persistent attributes;

  • the monitors, those the CSMS set and the hardwired and preconfigured ones, keyed by component and variable name, for every variable whoever owns it;

  • the values of persistent attributes of registered variables, which today is DER Enabled only.

Nothing is kept for the EVerest module configuration views or for external providers: the configuration service and the providers hold their values.

Monitors belong to OCPP, not to the owner of the variable, and are stored by name so that they outlive the registration that brought the variable. Until the owner registers, its variables are not part of the model and their monitors are kept, invisible to the CSMS, and active again with the same id once the owner registers the variable. A monitor whose owner registers without the variable, or whose variable no longer supports monitoring, is removed. The DER Enabled value the CSMS set follows the same rule. The removal happens at every start, after EVerest registered its components, so removing an EVSE or a grid_support connection, or switching an EVSE between AC and DC, removes the monitors and the Enabled value of the variables that go away.

Some variables are registered in OCPP 2.x mode only: the DER controllers, since DER is not supported in OCPP 1.6 mode, and the AvailabilityState of the EVSEs and connectors, which libocpp registers for its OCPP 2.x charge point unless the component configuration defines it. A start in OCPP 1.6 mode removes the monitors and stored values a CSMS set on them in OCPP 2.x mode. At the next start in OCPP 2.x mode, DER Enabled is back at its default true and the CSMS has to set it and the monitors again; the DER controls the CSMS set before are kept. OCPP does not foresee a downgrade from OCPP 2.x to OCPP 1.6; the module supports it, but does not keep this state across it.

Earlier versions kept the components EVerest provides in a second database, EverestDeviceModelDatabasePath (deprecated). At the first start the module takes it over: the DER Enabled values the CSMS set are imported into the device model database and the file is renamed to *.migrated. The steps are in Migrate to the Combined OCPP Module.

Monitors¶

A monitor watches one variable and sends a NotifyEvent to the CSMS when the variable crosses a threshold, changes by more than a delta, or periodically. Only a variable with supportsMonitoring can have monitors. There are three kinds:

  • custom monitors, which the CSMS sets with SetVariableMonitoring and may change and clear;

  • preconfigured monitors, which the integrator declares and the CSMS may change;

  • hardwired monitors, which the integrator declares and the CSMS can neither change nor clear.

Monitoring is OCPP 2.x only. These variables control it:

Variable

Effect

MonitoringCtrlr / Enabled

Switches monitoring on; false in the standardized component configuration.

MonitoringCtrlr / ActiveMonitoringBase

The monitoring base the CSMS selected with SetMonitoringBase: All, FactoryDefault or HardWiredOnly, see What the CSMS can change. Without a value, the base is All.

MonitoringCtrlr / ActiveMonitoringLevel

The severity the CSMS selected with SetMonitoringLevel: only events of monitors of this severity or more severe (lower number) are sent (N05.FR.03).

MonitoringCtrlr / OfflineQueuingSeverity

While offline, events of monitors of this severity or more severe are queued and sent once online (N07.FR.04).

InternalCtrlr / MonitorsProcessingInterval

How often periodic monitors are evaluated, in seconds.

Hardwired and preconfigured monitors¶

Hardwired and preconfigured monitors are declared where the variable is defined. For a telemetry variable they are its default alarms.

  • A variable of the component configuration lists them in a monitors array next to its attributes.

  • A variable registered at runtime, such as one of an external provider, lists them in RegisteredVariable::monitors with the same fields.

The components EVerest provides and the module configuration views declare none.

For example, two hardwired thresholds and a preconfigured delta monitor on EVSE / Power in a component configuration:

"monitors": [
  {
    "value": 21950,
    "severity": 1,
    "transaction": false,
    "type": "UpperThreshold",
    "config_type": "HardWiredMonitor"
  },
  {
    "value": 100,
    "severity": 1,
    "transaction": false,
    "type": "LowerThreshold",
    "config_type": "HardWiredMonitor"
  },
  {
    "value": 100,
    "severity": 1,
    "transaction": false,
    "type": "Delta",
    "reference_value": "10700",
    "config_type": "PreconfiguredMonitor"
  }
]

type is a monitor type of OCPP, for example UpperThreshold, Delta or Periodic; severity is 0 (most severe) to 9; transaction limits the monitor to a running transaction. A delta monitor of the component configuration needs a reference_value: it is the starting point of the first delta and is used only when the monitor is first stored; afterwards the stored reference value, which follows every event sent, is kept. A registered monitor needs none: a new delta monitor starts from the current value of the variable. A monitor on a variable without supportsMonitoring stops the start when it is in the component configuration. A registered monitor that does not fit the variable, a threshold outside its limits for example, or that is declared as CustomMonitor, is ignored with a warning.

At a start and at a new registration¶

The database keeps every monitor by component and variable name, so monitors outlast restarts and re-registrations. A declared monitor is matched to the stored monitor of the same variable with the same type and severity (N04.FR.10); the matched monitor keeps its id and its reference value.

The monitors of the component configuration are applied at every start. They are compared only with the stored hardwired and preconfigured monitors: a matched monitor takes the declared value, transaction flag and kind when they differ, a hardwired or preconfigured monitor that is no longer declared is removed, and an unmatched one is added. Custom monitors are left alone.

The monitors of a registration are applied whenever its owner registers, at every start and again whenever it registers anew. A stored hardwired or preconfigured monitor the registration no longer declares is removed, and so is any monitor, custom ones included, that does not fit the variable as registered. A matched stored monitor is handled by its kind:

Stored

Declared

Result

hardwired or preconfigured

hardwired or preconfigured

Takes the declared value, kind and transaction flag; written only when something differs.

custom

preconfigured

Kept: a preconfigured monitor the CSMS changed is stored as custom (N04.FR.15) and belongs to the CSMS.

custom

hardwired

Replaced by the hardwired monitor under the same id, with a warning in the log.

A variable that its owner no longer registers loses all its monitors, see What the database stores.

What the CSMS can change¶

  • SetVariableMonitoring adds custom monitors and changes a monitor by its id. A preconfigured monitor the CSMS changes becomes custom until a SetMonitoringBase resets it (N04.FR.15); a hardwired monitor cannot be changed (N04.FR.18).

  • ClearVariableMonitoring clears custom monitors; for a hardwired or preconfigured monitor it answers Rejected (N06.FR.03).

  • SetMonitoringBase selects the monitoring base (N03). All activates the preconfigured monitors and keeps the custom ones. FactoryDefault deletes the custom monitors, changed preconfigured ones included, and activates the preconfigured monitors. HardWiredOnly deletes the custom monitors and deactivates the preconfigured ones. The CSMS can add custom monitors on top of every base.

Known deviations from OCPP¶

libocpp deviates from OCPP in these points:

  • The monitoring base acts as a filter: under FactoryDefault no custom monitor is evaluated, under HardWiredOnly only hardwired monitors are, so a custom monitor the CSMS adds afterwards never triggers (#1994).

  • A preconfigured monitor the CSMS changed does not come back when SetMonitoringBase deletes the custom monitors, only at the next start or, for a registered variable, at the next registration (N03.FR.03, N03.FR.04; #1994).

  • SetVariableMonitoring with the id of a hardwired monitor is accepted and stores the changed monitor as custom (N04.FR.18; #3399). A registration that declares the hardwired monitor replaces it again.

  • A variable can have two monitors of the same type and severity (N04.FR.10; #3400): the component configuration adds a declared monitor again at the next start next to the custom monitor the CSMS changed it into, and a SetVariableMonitoring with an id is not checked for duplicates.

  • Events queued while offline are sent once online also when their severity is above ActiveMonitoringLevel (N07.FR.15; #3401).
